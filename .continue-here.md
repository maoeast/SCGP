Problems / blockers / risks:

- no active code blocker remains
- important implementation boundary:
  - current app persists each assessment scale in its own tables
  - FMDA should follow that pattern for now rather than introducing a repo-wide generic assessment schema as a prerequisite
- important FMDA detail boundary:
  - FMDA detail storage must preserve `is_auto_filled`
  - otherwise the basal/ceiling algorithm cannot distinguish a manual `0` from an auto-filled `0`, and IEP goal extraction will be wrong
- important report boundary:
  - `report_record.report_type` is protected by explicit CHECK constraints and migration rebuilds
  - `fine_motor` must be added consistently in `src/database/init.ts`, `src/database/migrate-report-constraints.ts`, and `src/database/migration/migrate-emotional-foundation.ts`
- important current-product boundary:
  - FMDA assessment entry is now reachable, but persistence and final report rendering are still incomplete
  - do not describe `fine_motor` as fully delivered until DB save chain and report persistence land
- important driver safety boundary:
  - the current driver includes a basal fallback when the domain has already been pushed back to its lowest item and still cannot establish a formal basal
  - this is intentional to prevent navigation deadlocks in the current UI flow, but it should be validated against expected clinical usage during runtime QA

Key decisions made in this conversation:

- integrate FMDA by continuing to reuse the existing `AssessmentContainer + ScaleDriver + per-scale tables + report_record` mainline
  - reason: this matches current code reality and avoids turning FMDA into a platform-wide assessment refactor
- ship `fine_motor` in slices:
  - first slice = entry wiring + generated question bank + driver logic
  - second slice = persistence tables + save chain + report-record wiring
  - reason: this keeps each step testable and limits breakage scope
- treat the FMDA source-of-truth as:
  - CSV question bank
  - expert-advice text file
  - reason: these two files are now aligned to the same 88-item item order and can safely drive generated question metadata
- implement Basal/Ceiling directly in the driver by mutating `state.answers` with auto-filled records
  - reason: the current AssessmentContainer passes a mutable `answers` object into `getNextQuestion`, which is the lowest-friction place to preserve `is_auto_filled` alongside navigation
- keep auto-filled answers in the same answer store as manual answers
  - reason: score calculation, progress, and later DB persistence all need one unified answer source with explicit `metadata.is_auto_filled`
