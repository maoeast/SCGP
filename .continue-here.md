Key decisions made in this conversation:

- split the login page into dedicated entry components
  - reason: the user explicitly requested componentized structure, and the old single-file login page mixed layout, form controls, and branding too tightly
- keep the login redesign outside the shared backend admin-page shell
  - reason: login is a standalone entry flow, not a backend business page
- use CSS variables plus JS `setProperty` for login theming
  - reason: the user explicitly required runtime primary-color changes and system-settings control
- store login theme and brand fields in existing `system_config`
  - reason: the repo already has a working local config persistence path, so this avoids inventing a second settings store or schema
- centralize theme application in `systemConfigStore` and bootstrap it from `main.ts`
  - reason: theme application should not depend on only the login page being opened first
- keep the palette blue-first and restrained
  - reason: the requested design direction was education-system, clean, simple, blue, and explicitly not purple / AI-style
- limit the first version to login-entry theming, not platform-wide theming
  - reason: broad theming would expand scope into many unrelated pages and settings consumers
