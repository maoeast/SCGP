Key decisions made in this conversation:

- integrate FMDA by continuing to reuse the existing `AssessmentContainer + ScaleDriver + per-scale tables + report_record` mainline
  - reason: this matches current code reality and avoids turning FMDA into a platform-wide assessment refactor
- ship `fine_motor` in slices:
  - first slice = entry wiring + generated question bank + driver logic
  - second slice = persistence tables + save chain + report-record wiring
  - third slice = config-driven report page backed by persisted FMDA data
  - reason: this keeps each step testable and limits breakage scope
- treat the FMDA source-of-truth as:
  - CSV question bank
  - expert-advice text file
  - reason: these two files are now aligned to the same 88-item item order and can safely drive generated question metadata
- implement Basal/Ceiling directly in the driver by mutating `state.answers` with auto-filled records
  - reason: the current AssessmentContainer passes a mutable `answers` object into `getNextQuestion`, which is the lowest-friction place to preserve `is_auto_filled` alongside navigation
- keep auto-filled answers in the same answer store as manual answers
  - reason: score calculation, progress, and later DB persistence all need one unified answer source with explicit `metadata.is_auto_filled`
- store FMDA report-critical derived data in two layers:
  - persisted aggregates in `fine_motor_assess`
  - persisted item-level truth in `fine_motor_assess_detail`
  - reason: the report can reuse saved totals but also safely recompute domain rates and IEP targets from detail rows when needed
- implement FMDA report interpretation by reading `ASSESSMENT_LIBRARY.fine_motor_preschool`
  - reason: keeps expert interpretation copy centralized in config rather than duplicating domain narrative in the page component
