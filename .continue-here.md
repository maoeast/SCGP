Key decisions made in this conversation:

- define `v1.7` around CNBS-R2016 integration only, and explicitly defer FMDA QA / training-record cleanup / resource-center redesign / platform debt
  - reason: mixing these tracks would create a fake milestone with weak acceptance boundaries
- treat the official `WS/T 580—2017` PDF as the normative scoring source
  - reason: the DQ threshold bands in prior draft materials drifted from the published standard
- integrate CNBS-R2016 through the current `AssessmentContainer + ScaleDriver + per-scale tables + report_record` mainline
  - reason: this matches current code reality and keeps the new scale aligned with the rest of the assessment platform
- make typed question-bank digitization the first execution phase
  - reason: without structured item data, there is nothing reliable to drive basal/ceiling logic, MA/DQ scoring, persistence, or reports
- split CNBS-R2016 config into light and heavy layers
  - reason: the heavy narrative feedback corpus is ~200 KB and would bloat `src/config/feedbackConfig.js`; later `Driver` logic only needs a small threshold/age-bracket/domain config while the report page can load the heavy narrative asset separately
- implement runtime DQ intervals as `>=130 / [110,130) / [80,110) / [70,80) / <70`
  - reason: the user explicitly chose a fully covered programmatic interval model to avoid edge-case gaps while preserving the official PDF intent
- digitize the 261 items directly from the official PDF instead of `核心引擎数据.zip`
  - reason: the zip asset does not contain the question bank, while the PDF is the canonical source for the item table and pass criteria
- do not re-run GSD orchestration for this phase execution
  - reason: Phase 17 was already fully planned in `.planning/`, and direct execution was faster and less noisy than re-entering the planner/executor loop
