Key decisions made in this conversation:

- bridge `game_emotion_records` into the existing training-record UI before doing the larger schema rewrite
  - reason: the user-visible bug was “records not showing”, so restoring list/count/detail visibility was the shortest correct fix
- add a lightweight emotional mini-game detail page now instead of leaving records with no drill-down
  - reason: surfacing records without any detail path would leave the record chain incomplete for review and debugging
- plan the long-term design as:
  - one unified training-session main table
  - plus a small number of family detail tables
  - not one table per game
  - reason: per-game tables do not scale and would make menu counts, reports, authorization, and migration much harder
- keep module activation and procurement boundaries at the product/query layer, not the physical table layer
  - reason: authorization is a business concern and should continue to be controlled by `module_code / entry_code / route/menu guards`, not by exploding the schema into parallel per-module summary tables
