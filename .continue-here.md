Key decisions made in this conversation:

- land Phase A schema/init and the first safe dual-write slice in the same round
  - reason: schema alone would be too inert to verify, while emotional write paths are relatively isolated and low-blast-radius
- use `source_table + source_record_id` as the unified summary upsert key
  - reason: this gives an idempotent migration identity and avoids duplicate `training_session` rows on retry / repeated writes
- keep `training_session` strictly as summary-level storage for now
  - reason: the current plan still keeps family detail tables separate instead of forcing premature detail-table migration
- do not switch any current consumer read path to `training_session` yet
  - reason: keep rollout phase-separated and reduce regression surface before sensory/equipment dual-write is complete
- start dual-write with emotional scene and emotional mini-game paths before sensory/equipment
  - reason: those two paths were already isolated and easier to normalize against the new summary schema
- once sensory game and equipment writes are connected, move the next risk-controlled phase to read-chain migration instead of expanding schema again
  - reason: Phase B write coverage is now complete enough to start validating `training_session` as the future summary fact source
- wrap sensory game and equipment dual-write in the same transaction as the legacy insert
  - reason: avoid partial success where the old table insert lands but the unified summary write fails
- trigger sensory game save at the actual game-completion event instead of a second result-page button click
  - reason: runtime verification showed the old interaction model made sensory saves easy to skip and did not match the implicit expectation that “training finished” already means “record persisted”
- only persist `training_session.task_id` when the current `task` table actually contains that task row
  - reason: current code reality still allows sensory game records without seeded `task` rows, so forcing the legacy front-end `TaskID` through the new summary-table foreign key can roll back the whole save
