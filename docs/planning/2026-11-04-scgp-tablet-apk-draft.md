# SCGP 平板现场训练端：产品与技术初稿

> 日期：2026-11-04（讨论始于 2026-11-03） · 版本：v0.1 · 状态：待 Claude / Gemini 审查
>
> 用户已确认产品范围、与 PC 保持视觉一致、Android APK、单校一台 PC 服务多台平板，以及两端共用教师账号。本文件的技术选型与实现方式是推荐方案，尚未实施。
>
> 原则：先打通真实业务，再根据使用反馈完善。首版不展开复杂同步系统、云平台或全仓重构。

## 1. 产品定位与首版范围

平板是 SCGP 的现场训练端。PC 负责学校数据、账号管理、计划编排和汇总；老师拿平板到学生身边执行训练并记录。

典型场景：学校在一台电脑安装 SCGP，开启局域网服务。多位老师使用各自的现有账号，同时在不同平板上开展训练。平板也可以退出账号，再由另一位老师登录使用。

| 首版功能 | 具体范围 |
|---|---|
| 今日任务 | 查看本人的有效训练计划与待执行资源，直接启动 |
| 学生速查 | 查看本人负责学生、基础信息和有限近期训练记录 |
| 生活自理任务执行 | 查看步骤图片/音视频，记录每一步的完成等级与简短备注 |
| 器材训练记录 | 选择器材，填写训练评分、辅助等级、时长和备注，连续录入 |
| 近期记录回看 | 按学生查看记录，确认刚才保存的结果 |
| 局域网数据访问与离线暂存 | 从 PC 获取数据和所需素材，本地保存现场记录，恢复连接后回传 |

首版暂不接入完整评估、小游戏、AI 助手、资源编辑、完整报告生成、账号管理和复杂计划编辑。后续是否接入，按现场使用需求决定。

## 2. 推荐技术栈

**Vue 3 + TypeScript + Vite + Pinia + Capacitor Android + SQL.js，打包为 APK。**

| 层次 | 推荐选择 | 原因 |
|---|---|---|
| 页面与交互 | Vue 3、TypeScript、Vite | 与 PC 一致，便于复用业务定义与样式 |
| 状态管理 | Pinia、Vue Router | 沿用现有开发方式 |
| Android 外壳 | Capacitor 8.x | 将 Vue 前端打包为 Android 应用，接入文件与生命周期能力 |
| 本地数据 | SQL.js + Android 应用私有目录 | 沿用现有数据库技术；平板只保存所需数据和现场记录 |
| 局域网请求 | CapacitorHttp | 通过原生网络请求访问 PC 的有限业务 API |
| 素材下载 | 官方 File Transfer / Filesystem 插件 | 将任务所需图片、音视频保存到本地 |
| PC 服务 | Electron Main + Node 内置 HTTP 服务 | 利用现有桌面运行环境，不新增独立服务器安装程序 |

Capacitor 是 Android 外壳选择，不要求采用 Ionic 的界面风格。平板继续使用 SCGP 的视觉语言。

UI 以 Vue 组件和共享 CSS 为主。Element Plus 中适合平板的组件可以按需使用；现场评分按钮和任务操作区按触控逻辑编写。首版不引入另一套完整 UI 库。

Capacitor 当前稳定文档为 v8，环境要求 Node 22+、Android Studio 2025.2.1+；8.x 对应 target SDK 36。具体补丁版本在建立 APK 工程时锁定。[Android 文档](https://capacitorjs.com/docs/android)、[环境要求](https://capacitorjs.com/docs/getting-started/environment-setup)、[SDK 对照](https://capacitorjs.com/docs/android/setting-target-sdk)

Flutter 或纯原生 Android 都能实现，但需要重新构建大部分界面与前端业务。以当前首版范围和视觉一致要求，优先选用 Capacitor。此结论仍需首个真机闭环确认。

代码组织建议：在现有仓库增加独立的 `apps/tablet/` 入口与 Android 工程。先窄范围共享纯业务定义和样式，PC 保持现有入口。暂不整体改造为新的工作区或重写数据库架构。

## 3. 视觉一致：沿用 PC 设计系统，重排平板布局

### 3.1 共用的视觉基础

以当前 `src/assets/layout.css:7-29` 为公共视觉基线，复用机构 Logo、产品名称、学生头像、图标、入口名称和颜色语义。平板身份仍是 SCGP，可使用“现场训练”作为页面说明。

| 项目 | 当前 PC 基线 |
|---|---|
| 页面背景 | `#eef2f6`，柔和背景 `#f8fbff` |
| 卡片 | 白色 `#ffffff`，次级表面 `#f7fafc` |
| 主色 | `#5f89d9`，浅底 `#edf4ff` |
| 主文字 / 次级文字 | `#303133` / `#606266` |
| 边框 | `#e6ebf2` |
| 成功 / 警告 / 错误 | `#2aa071` / `#ba7517` / `#d85d55` |
| 卡片圆角 | 18px / 22px |
| 导航 | 沿用 PC 深蓝导航壳的识别特征，缩减占用空间 |

PC 当前存在场景主题差异，不能假设所有页面已经使用同一套颜色：

- 生活自理执行页已有米色、木色、绿色的训练主题，平板对应场景继续沿用。
- 器材与训练入口的主题色取自 `src/utils/training-entry.ts:36-105`，不另建平板配色表。
- 共享的颜色与主题声明保持一个来源；允许两端采用不同尺寸、间距和排版。
- 字号层级、字重和行距保持同类关系。Windows 与 Android 的实际中文字形需要在真机上对照，不能仅凭相同字体列表承诺完全相同。

首个界面产物制作前，先提取/引用上述公共 token 和训练主题。保留品牌一致性所需的范围，不顺带统一全部 PC 历史样式。

### 3.2 平板布局

以 10–12 英寸平板为首批验证场景，横屏优先，同时让竖屏可完成主要操作。具体尺寸与 Android 版本待目标设备确定。

- **应用首页**：今日任务为主，学生与记录为辅。导航建议为“今日、学生、记录、我的”。宽屏使用窄导航轨，窄屏使用底部导航。
- **任务列表**：学生、任务名称、资源、上次表现与开始按钮组成任务卡，不照搬 PC 多列表格。
- **生活自理横屏**：步骤示范与记录区并排；记录按钮在容易触及的位置。窄屏将评分操作放在步骤下方的固定操作区，避免被长内容推到屏幕底部之外。
- **器材训练**：选定学生与器材后，以评分和辅助等级为主体。资源列表按需要展开，保存后原位反馈，并可继续录入。
- **训练执行中**：收起普通导航，持续显示学生与任务；详细备注按需展开，主要操作不依赖键盘或悬停。

触控尺寸初始建议：普通操作区域至少约 48–52 CSS px，核心评分按钮约 64 CSS px 或更高，最终按真机手感调整。这些是设计起点，不是已经验证的设备参数。布局按可用窗口宽度变化，不按物理分辨率写死。

### 3.3 保留 PC 的业务含义

| 场景 | 保留的字段与等级 |
|---|---|
| 生活自理 | 独立完成、口头提示、协助完成、未完成；逐步结果与备注 |
| 器材训练 | 1–5 分训练评分；独立、口头、视觉、手触、身体五级辅助；时长与备注 |

两类训练的评分结构不同，平板只调整操作呈现，不将其合并为同一套等级。独立完成比例与任务完成比例分别显示。

首版以老师记录为主。生活自理的步骤示范可以供学生观看，但不额外建设完整的学生账号和学生应用。

## 4. 一台 PC 服务多台平板

### 4.1 推荐工作方式

1. 管理员在 PC 的设置中开启“平板连接服务”。
2. PC 显示局域网地址与连接状态。首版支持手动输入或保存地址，扫码连接可后补。
3. 平板连接学校 PC，输入与 PC 相同的教师账号和密码。
4. PC 校验账号，返回该教师可见的学生、计划、训练资源和近期记录。
5. 老师开始训练，平板先保存本地记录，有连接时回传 PC。
6. PC 保存记录后，平板显示已回传；PC 的记录页面能够查询到结果。

学校网络需要允许平板访问这台 PC。PC 应用运行且数据服务就绪时提供在线访问。Windows 当前关闭主窗口会退出应用，所以首版说明为“服务使用期间保持 PC 应用运行”；最小化后的响应在首个真机闭环中核查。暂不建设 Windows 后台服务或托盘常驻。

### 4.2 同一套教师账号，支持切换

- 账号和密码由 PC 现有用户管理维护，平板不新增另一套账号库。
- 每台平板独立登录。多台平板的教师会话互不改变，也不改变 PC 界面的当前登录人。
- 同一台平板支持退出登录，再用另一位教师账号登录。
- 获取学生与提交记录时，使用该平板会话中的实际教师身份，沿用 PC 的任教班级学生范围。
- 退出前未回传的记录保留原教师归属；原教师下次登录后继续回传。切换到其他账号时，不展示上一账号的工作区。
- 首版要求连接 PC 才能登录和切换账号。已登录教师可以离线执行已经领取并准备好素材的任务。

现有 `UserAPI.login(username,password)` 可复用账号校验逻辑。不能调用 PC 的 `authStore.login()` 来代替远端登录，因为它会改变 PC 本机登录状态。教师范围可复用 `buildTeacherStudentScope(alias,{role,userId})` 的显式身份模式。

### 4.3 接入现有数据链

```mermaid
flowchart LR
  A[多台平板 APK<br/>各自教师会话与本地记录] --> B[PC Main 局域网 API]
  B --> C[IPC 业务请求]
  C --> D[Renderer 应用级数据服务]
  D --> E[现有唯一 SQL.js 数据实例]
  E --> F[现有 Main 文件保存]
```

当前 SQL.js 数据在 Renderer 里。Main 的局域网服务通过新增的有限 IPC 业务接口访问它，数据服务在应用初始化后注册，独立于首页等路由页面。

Main 不另开第二个可写数据库副本。需要调整的内容限于局域网入口、显式教师上下文和可确认的保存结果。

PC 服务使用 Node 内置 HTTP 能力与 Electron IPC 即可起步。[Node HTTP](https://nodejs.org/docs/latest-v20.x/api/http.html)、[Electron IPC](https://www.electronjs.org/docs/latest/tutorial/ipc)

首批业务 API 只需覆盖：连接状态、教师登录/退出、当前教师数据、训练素材下载、提交训练结果和查询近期记录。地址、会话与请求协议在首个闭环阶段确定，不提前建设通用后端框架。

APK 自带平板界面，通过 `CapacitorHttp` 请求数据。它提供原生请求能力；Android 局域网访问及 HTTP/HTTPS 配置按目标 SDK 在真机联调时确认。[HTTP API](https://capacitorjs.com/docs/apis/http)、[Android 网络配置](https://developer.android.com/privacy-and-security/security-config)、[局域网访问说明](https://developer.android.com/privacy-and-security/local-network-permission)

## 5. 首版数据处理规则

### 5.1 今日任务采用现有计划逻辑

当前 `DashboardAPI.getTodaySchedule()` 查询有效期内的 active 计划，并为每个计划选取第一条可启动资源。现有系统没有精确排课和每日任务实例。

首版保留这一现实：平板“今日任务”展示当前教师有效计划的可执行入口，可展开计划内支持的自理/器材资源。记录保存计划与资源来源。暂不新增排课系统，不将一次训练自动等同于整个计划完成。

### 5.2 现场记录与回传

- 每条记录保留实际教师、学生、资源、计划来源、原始发生时间和训练结果，并有用于回传识别的稳定记录 ID。
- 自理按步骤保存本地草稿，结束时形成正式训练记录；未评分状态不默认算成独立完成。
- 器材沿用现有整次记录的字段。首版不扩展为复杂的逐试次采集。
- 平板状态只区分“本地已保存、待回传、已回传”。只有 PC 确认保存后才显示已回传。
- 断开连接时继续使用已准备的数据和素材，恢复连接后提交待回传记录。APK 关闭再打开后，应能恢复已保存内容。
- 两位老师的记录各自保存并汇入同一学生档案。相同学生或资源的两次真实训练仍是两条记录。

当前保存 API 尚无 `planId`；器材支持教师名称，自理尚无教师字段。实现时补充必要的来源关联，保留训练时的教师、时间、班级和资源快照，不用回传时的当前信息替代。

沿用现有“业务源记录 + `training_session`”写入方式。避免让平板记录形成另一套只在专属页面可见的数据。

### 5.3 平板本地保存与素材

当前 `SQLWrapper` 的自动保存依赖 Electron。平板需要一个小型存储适配，负责将 SQL.js 数据保存到 Android 私有目录；业务操作完成实际写入后再显示本地保存成功。

图片、视频和音频需要下载真实文件。PC 的 `resource://` 地址经平板资源适配转为本地可播放地址。只准备本次需要的素材，不复制学校整个资源库。

可使用官方 Filesystem 的 `readFile/writeFile/getUri` 与 Capacitor 的 `convertFileSrc`；较大素材通过 File Transfer 下载，不经 JSON 返回整段 base64。[Filesystem](https://capacitorjs.com/docs/apis/filesystem)、[本地 URL 转换](https://capacitorjs.com/docs/core-apis/web)、[File Transfer](https://capacitorjs.com/docs/apis/file-transfer)

## 6. 最小实施顺序

| 阶段 | 做什么 | 完成证据 |
|---|---|---|
| 0：现状核对 | 核对样式、账号、业务 API 与官方平台能力 | 本初稿已记录来源；运行能力尚未验证 |
| 1：真实闭环 | 建立 APK 入口，PC 开服务；一个现有教师账号登录；领取一个自理任务，播放一个本地素材，保存并回传一条结果 | 真机 APK 与 PC 能查到同一条真实记录 |
| 2：首版业务 | 接入今日任务、学生速查、自理执行、器材录入和近期回看；完善两类平板布局 | 老师可连续完成两类训练并回查 |
| 3：多教师使用 | 两位老师两台平板同时使用；同一平板换账号；断网记录后恢复连接回传 | 账号、任务、记录归属正确，已保存内容可恢复 |
| 4：用户试用 | 对照 PC 确认颜色与界面识别，在实际训练场地使用 | 用户确认操作路径和首版范围可用 |

先证明功能路径与真实设备使用。不在本轮增加自动化测试体系、回归保护或与首版无关的改造；用户确认使用没有问题后，再按需要完善。

首版推荐一台学校 PC 作为数据来源。具体并发容量和支持的平板型号由实际运行结果确定，不预先承诺设备数量。现有 PC 激活是机器绑定的，平板如何计入产品授权需另行确定，本初稿不改变现有商业授权规则。

## 7. 审查重点

请 Claude 和 Gemini 重点回答以下问题，并优先提出更简单的可行实现：

1. 推荐技术栈能否直接服务本次首版，是否存在必须更换技术的真实阻碍？
2. 颜色、组件和训练主题的复用边界，是否足以让老师识别为同一个 SCGP？
3. 平板布局是否便于老师观察孩子、快速记录，是否还有不必要的点击和输入？
4. 多平板登录是否始终使用各自教师身份，是否会错误复用 PC 当前登录人？
5. 局域网请求接入唯一 SQL.js 实例、保存后回执与离线补传，能否用更少改动打通？
6. 今日任务、两类评分、独立率和记录归属是否忠实于当前实现？

只把阻断首版的事项列为必须修改。未来可能有用的功能单独简短列出，不纳入首版实施范围。
