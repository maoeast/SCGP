# 2026-03-26 Project Context Archive

本文档用于承接从 `PROJECT_CONTEXT.md` 高热入口中迁出的历史内容摘要。

## 为什么归档

此前 `PROJECT_CONTEXT.md` 同时承担了：

- 当前有效协作摘要
- 历史阶段流水
- 已完成功能长列表
- 旧 Phase 计划与旧下一步建议
- 大量已经过期或失效的上下文

这会导致两个问题：

- 每次新会话读取成本过高
- 当前有效事实被历史内容淹没

因此从 2026-03-26 起：

- `PROJECT_CONTEXT.md` 只保留当前有效上下文
- 历史完成项与阶段流水转移到本归档摘要、`docs/CHANGELOG.md` 与 git history

## 已迁出的历史内容类型

以下内容不再保留在高频启动入口里：

- 旧版 Phase 0 ~ Phase 5.2 长表格
- 已完成的旧阶段执行日志
- 已过期的“下一步计划 / 待办事项”
- 历史量表实现细节长说明
- 旧版 Dashboard 命名阶段描述
- 过长的 Conners / CSIRS / 旧评估模块技术细节
- 已关闭或已被后续实现替代的问题清单

## 仍然保留历史信息的位置

- 详细完成项时间线：
  - `docs/CHANGELOG.md`
- 仓库真实演进记录：
  - git history
- 旧规划与旧设计稿：
  - `docs/plans/`
  - `docs/architecture/`
  - 其他带“历史 / 旧交付稿 / 原始需求”标记的文档

## 截至归档时仍值得记住的历史结论

- `sensory` 是长期以来最完整的业务主链
- `emotional` 已逐步从占位走向可运行，但仍处于持续补完阶段
- 路由和导航层长期落后于模块化与资源化底座
- 顶层授权模型已稳定为真实业务 `moduleCode`，不应被内部入口概念污染
- 文档长期存在“目标态覆盖现实态”的风险，因此后续必须更严格地按代码现状写文档

- 如果只是开启新会话，不要先读本归档文档

- 若后续 `PROJECT_CONTEXT.md` 再次明显膨胀，应继续把历史部分迁出到新的归档摘要，而不是恢复长流水结构
